Compiling EYG effects to JavaScript

Generalized evidence passing and JavaScript generators as two backends for one typed A-normal form. Every technique from Xie and Leijen (ICFP 2021) is implemented behind a switch, measured in Bun and Chromium against the interpreter, and used to run browser effects designed for the DOM, signals and WebRTC.

4 million tail resumptive performs with every optimisation, Bun.
53×

60–360×

The starting point

The gleam_compiler package transpiled EYG to JavaScript that looked like the source. An effectful let became bind(value, then), a perform returned an Eff object, and every caller checked instanceof Eff. Its own README called this out: there was no evidence passing, every effect bubbled to its handler, and a faster version was future work.

Porting the spec suites and a differential test against the interpreter showed it was also wrong in places that had nothing to do with effects:

  • !list_fold called the reducer as f(acc)(item); the interpreter calls f(item)(acc).
  • !int_compare tested y > x twice, so it never returned Gt.
  • !string_starts_with returned the old Ok(rest) shape, the spec now returns a boolean.
  • String literals were HTML escaped, "a<b" compiled to "a&lt;b".
  • !fix, binaries and handlers that do not resume immediately were not supported, and the host effects were hard coded to Alert, Ask and Log.

The replacement keeps the idea that generated code should be plain JavaScript functions over plain values, and changes everything about how effects move.

EYG effects in one screen

Four properties of EYG decide what a compiler has to support.

  • One operation per label. perform Ask({}) sends a value to the innermost handler for Ask. A handler is handle Ask(clause, exec) and a clause is (value, resume) -> { ... }.
  • Handlers and resumptions are values. A clause can be bound to a variable, passed around, or return resume itself. Nothing about a handler is syntax the compiler can rely on.
  • Deep and multi-shot. Resuming reinstalls the handler, and resume can be called zero, one or many times.
  • Effect rows are inferred. Every function type carries a row of the effects calling it can perform. Rows are open and generalised at let.
handle Choose((options, resume) -> {
  // multi-shot: resume once for every option
  !list_fold(options, 0, (col, acc) -> { !int_add(acc, resume(col)) })
}, (_) -> { place(0, []) })

Pipeline

Both backends share analysis and normalisation. The analysis gives every node a resolved type; A-normal form uses the types to mark each call as checked or not, and the renderers only differ in what a checked call becomes.

The paper, checked technique by technique

Xie and Leijen refine algebraic effects in steps: multi-prompt delimited control, evidence passing, bubbling yields, and a monadic translation that can be compiled to anything. The Koka C backend adds canonical evidence vectors, short-cut resumptions, bind inlining and join points. The table records which of those the EYG compiler implements and the switch that turns each off. Evidence and why there is no static index

Performing looks up evidence instead of walking up the stack. The compiler emits the lookup at the perform site, $s.w.Ask, so V8 and JavaScriptCore cache the property access for each site rather than for a shared helper. Installing a handler copies the vector, which is why insertion order is still worth comparing: it is cheap to install and linear to search. With ten unused handlers between the loop and its reader the linked list costs three times as much, while the map is flat.

Koka goes further and indexes a canonical vector at a constant offset known at compile time. That needs the row at the perform site to be closed and the vector at runtime to have exactly that shape. In EYG neither holds. Rows inside let bound functions are open, inference unifies rows rather than inserting open coercions that would rebuild vectors at call boundaries, and a non-scoped resumption can run under more handlers than its type mentions. A property lookup keyed by label, specialised by the engine, is the practical constant time lookup.

Tail resumptive clauses, and the subtle part

Most handlers resume exactly once, in tail position: a reader, a logger, a platform call. The compiler recognises any lambda of the form (value) -> (resume) -> { ...; resume(e) }, where every tail position calls resume and resume appears nowhere else, including through matches. It emits the lambda with a second version attached, the body with resume(e) replaced by e. Because the mark is on the function value, a handler bound to a variable or built by a helper is optimised too, which answers the open question in the old README.

$handle("Ask", $tr(
  (_) => (resume) => resume(1),   // the clause as written
  (_) => 1                        // evaluated in place by perform
), exec)

When the evidence has an in-place version, perform runs it immediately under the evidence vector the handler was installed in. No continuation is captured and nothing moves on the stack. The subtle case is a clause that yields to an outer handler and whose resumption is later run under different handlers. The paper shows that fixing the evidence vector at that point is well typed and wrong; underk has to find the evidence for the label again when resumed. The runtime does exactly that, and section 2.12.2 of the paper is one of the tests.

function performWith(ev, value) {
  const t = ev.t;
  if (t !== null) {             // tail resumptive: run the clause here
    const w = s.w; s.w = ev.w;
    const r = t(value);
    s.w = w;
    if (s.y !== null) { under(ev.l); return; }  // re-find evidence on resume
    return r;
  }
  s.y = { l: ev.l, m: ev, v: value, k: [] };     // yield to the marker
}

Yields, frames and short-cut resumptions

The monad of the paper is never allocated. As in Koka's C backend a function returns normally when it did not yield and sets $s.y when it did, in which case its return value is ignored. Every frame a yield leaves adds itself to the resumption. With short-cut resumptions the resumption is an array of frames, innermost first; resuming folds over it one frame at a time and, if a frame yields again, appends the rest of the array to the new yield. Without them each frame wraps the previous resumption in a closure, which costs an allocation per frame and a JavaScript stack frame per frame on resume. The difference shows where resumptions are long and frequent, in nqueens and mstate.

Bind inlining and join points

A naive monadic translation turns every effectful let into a bind with a closure for the rest of the block. That closure is allocated even when nothing yields, and it hides every tail call. The compiler inlines the bind instead: the fast path continues in place, and only the slow path allocates a frame. The frame calls a join point, the rest of the block lifted to the top of the program with its free variables as arguments. A join point uses a plain bind for the next checked call and jumps to the next join point, so each statement is emitted twice at most, never 2n times.

For comparison, the same loop with inlining switched off and as a generator:

// inline: false, the continuation is allocated on every iteration
(acc) => $bind($performWith($s.w.Ask, $unit), (t) => $int_add(acc, t))

// generator
(function* (acc) { const t = yield {l: "Ask", v: $unit}; return $int_add(acc, t); })

Type selective translation

A call is checked only when the function called has an effect row that is not empty. The analysis records the row of every function type, so the decision is made per call rather than per function as in Koka. Two details of EYG's inference mattered. The effect annotation on a call node is the part of the row that would generalise, which can say empty for a call through a parameter; the callee's type is used instead. Variables are annotated with an opened type, so a call through a variable to a pure let bound function is still checked. That costs a flag test and a join point, and is the first thing to improve.

Non-scoped resumptions

Evidence passing translation, the earlier technique, fixes evidence when a program is elaborated and fails at runtime if a resumption escapes its handler. Generalised evidence passing reinstalls the prompt on the evidence current at resumption. Both examples from section 2.12 are tests: a resumption returned from an Evil handler and resumed under a different reader must read 2, and the same from inside a tail resumptive clause. EYG has no recursive types, so the escaping resumption does not type check; the compiler falls back to checking every call and the tests still pass for every configuration.

Each technique, measured

The benchmarks are the ones Koka's paper uses, written in EYG. counter performs a tail resumptive reader four million times; counter1 and counter10 put one and ten unused handlers in between; host performs a synchronous platform effect; mstate threads state through resumptions captured under a lambda; nqueens resumes once per column. fib has no effects and polymorphic calls an effect polymorphic map with a pure function. Each case runs in its own process or browser context, ten times, the first three dropped; bars are the median relative to every optimisation on.

Sizes: fib 30, counters and host 2000² performs, polymorphic 1000², mstate 10 000, nqueens 9. host varies up to two times between runs in both engines, every run is pooled.

Reading the results

Effects that resume once. On counter the tail resumptive optimisation is worth fourteen times and evidence lookup, against bubbling, eleven. Put ten unused handlers in the way and the full configuration does not move, 31 to 32 milliseconds, while the linked list costs three times as much, bubbling fifty-three times and yielding without tail resumption a hundred and twenty. This is the shape of the paper's Figure 6, and the reason tail resumption matters: most real handlers are readers, loggers and platform calls.

Pure code. fib performs no effects, so evidence and tail resumption cannot help it. Checking every call and allocating a continuation for every bind each cost more than twice as much. polymorphic tells the same story through an effect polymorphic map: its body is checked because its row is open, and the calls at a pure type are not.

Multi-shot resumptions. nqueens yields on every choice whatever the configuration, so the fast path does not help. Short-cut resumptions are worth half as much again, and bubbling is the fastest configuration: every resumption reinstalls its handler, and copying the evidence object on every reinstall costs more than bubbling past the few handlers that are there. mstate at 10 000 operations takes about eight milliseconds, too little to separate the configurations from noise; at 200 000 it overflows the stack in every configuration, because a resumption that is not tail resumptive re-enters the prompt from inside the previous clause.

Host effects. host performs Random through the platform. As a root clause it runs in place and costs about the same as the reader. It is also the noisiest benchmark, with the same configuration varying up to two times between processes as the JIT inlines differently.

V8. Chromium tells a different story in two ways. First, anything that resumes through the prompt fails outright: bubbling and yielding without tail resumption overflow the stack on every counter, and every configuration of mstate overflows at 10 000 operations, where JavaScriptCore finished all of them in milliseconds. JavaScriptCore eliminates the tail calls from a clause back into its resumption; V8 does not, so on V8 the tail resumptive optimisation decides whether a loop of effects runs. Second, V8 removes much of what inlining and selectivity save by hand: on the counters, allocating a closure per bind or checking every call costs almost nothing, and on fib configurations with identical generated code differ by half again, which is JIT noise, not a measurement. Evidence still matters, the linked list grows from level to nearly twice as slow with ten unused handlers while the map stays flat, and generators are worst of all, eleven seconds for counter and a crashed renderer once handlers are nested.

Correctness

Every configuration, eight evidence passing variants and two generator variants, runs the same three suites.

  • Spec suites. spec/evaluation core, builtins and effects, the contract every EYG implementation shares.
  • Differential. 1 200 programs built from the type rules by the generator on the find-soundness-bugs branch, sizes 10, 20 and 35, including handlers, recursion and polymorphism. Every program the interpreter finishes must produce the same value compiled.
  • Targeted. Nested handlers, clauses performing outer effects, multi-shot resumption, effectful folds and recursion, and the two non-scoped resumption examples.

The differential test found three bugs while the backends were written: an effectful return assigned inside a match was not treated as yielding; the analysis annotates a lambda with a closed row while calls in its body keep the open row, so a generator function could not be decided from its type; and generators nested a new handler loop inside every clause, which overflowed the stack after a few thousand effects.

Generators

How the translation works

A generator function suspends at yield and keeps its locals, which is most of a continuation already. The generator backend turns a lambda whose body can yield into function*, a perform into yield {l, v}, and an effectful call into delegation with yield*. A handler is a generator that drives the handled computation:

function* loop(label, h, exec, gen, input, history) {
  while (true) {
    const step = gen.next(input);
    if (step.done) return step.value;
    const request = step.value;
    if (request.l !== label) { input = yield request; continue; }  // not ours, pass it up
    if (h.t) { input = yield* run(h.t(request.v)); continue; }   // tail resumptive, stay in the loop
    const resume = (x) => loop(label, h, exec, gen, x, …);   // deep, one shot
    return yield* run(h(request.v)(resume));
  }
}

Nothing like join points or frames is needed, the compiler is a third the size of the evidence backend. The cost moves to runtime: a request travels up every yield* between the perform and its handler and the reply travels back down, as in the diagram above.

Ergonomics

  • Function colour. A generator function called like a normal function returns an iterator, not a value. EYG generalises effect rows, so the same function is used at pure and effectful types, and a callee cannot be known from the call site. Every call result is tested with isGen, and a pure call of a generator is driven to completion. Evidence passing has one representation for every function; the types only remove checks.
  • Deciding a generator. The type of a lambda is not enough, the body decides. Getting this wrong is a syntax error, not a slow path.
  • One-shot continuations. A generator cannot be cloned. A resumption used a second time replays the handled computation from the start, feeding it every reply it had. That is sound only because EYG is pure apart from effects, and it is quadratic: nqueens is two orders of magnitude slower.
  • Deep handlers nest. A clause that calls resume starts the rest of the computation inside itself. Without the tail resumptive optimisation every perform adds a level of delegation and ten thousand effects overflow the stack. Tail clauses are evaluated in the loop, the same technique as the paper. mstate still overflows.
  • Async is natural. The top level drives the outermost generator and awaits host promises between steps. The evidence runtime does the same with a yield at the root, so this is a tie.
  • Readable output and stack traces. Generated generators read like the source, and a stack trace shows the chain of generators. The evidence output is readable on the fast path; the slow path is spread over join points.

Measured

In Bun, generators are seven times slower than evidence passing on fib, a program with no effects at all: every call result is tested with isGen and every effect polymorphic function allocates an iterator. On polymorphic the gap is eleven times. Where effects happen the cost scales with the depth of delegation: 95 times on counter, where each of the four million performs climbs five generators and comes back, and 110 times on nqueens, where every extra resumption replays the search from the start. Without tail clauses in the loop the counters overflow the stack, and mstate, whose clause is not tail resumptive, overflows either way.

Generators cost least where the host dominates. In the browser experiments below, DOM work and network delivery hide the difference whenever a design performs a handful of effects.

Against the interpreter

The interpreter is a CEK machine written in Gleam, compiled to JavaScript and run by Bun. It is the reference implementation, not a fast one. The compiled programs were run at the smaller sizes the interpreter can finish.

Designing effects for browser APIs

Three rules of EYG shape every design, and they are rules of the language, not of this compiler.

  • Every value can be serialised. A DOM node, a peer connection or a signal cannot be a value. A program can refer to one by an integer handle, by a selector, or not at all.
  • There are no recursive types. A tree cannot be typed. A DOM subtree is a flat list of nodes with their depth, the shape DecodeJSON already uses for JSON.
  • Effect types are monomorphic. Signal cannot be generic in its value. The host designs use strings.

Each design below is a separate platform with its own effects, types in Gleam next to the runtime, and the same task written against each in examples/browser. A test type checks every example against its design and nothing else. The tables are measured in Chromium, five runs after two warm up, on a fresh fixture every time, for both backends; effects is the number performed in one run.

The DOM itself: reading

Task: sum the numbers in a table of 1 000 rows and five columns.

// handles
Query     : String -> Result(List(Int), String)
ReadText  : Int -> Result(String, String)
// selectors
ReadText  : String -> Result(String, String)
ReadAll   : String -> Result(List(String), String)
// snapshot
Snapshot  : String -> Result(List({depth: Int, node: Element({tag, attributes}) | Text(String)}), String)

Crossing into the host is cheap with evidence passing. A synchronous effect is a tail resumptive clause at the root of the evidence vector, so 5 001 handle reads cost about a microsecond each including the DOM. What is expensive is making the host answer a question badly: a selector per cell makes the page run :nth-child queries 5 000 times and is almost forty times slower than handles.

The snapshot is one effect, but the program then walks eleven thousand records in EYG, so it is slower than reading with handles and four times slower than ReadAll, which asks the page the one question the program cannot answer cheaply. With generators every effect climbs the generator chain, so the design with 5 001 effects triples in cost while the single effect designs barely move.

Creating and editing elements

Task: create 1 000 rows of two cells, change the label of every tenth, then remove every row.

// imperative, one effect per operation on handles
CreateElement : String -> Result(Int, String)
Append        : {parent: Int, child: Int} -> Result({}, String)
SetText       : {node: Int, text: String} -> Result({}, String)
// patch, a list of operations in one effect, New(i) refers to the i-th created node
Patch  : List(Create(String) | CreateText(String) | Append({parent: Ref, child: Ref}) | …) -> Result(List(Int), String)
// render, describe the children, the page reconciles
Render : {selector: String, nodes: List({depth: Int, node: Element(…) | Text(String)})} -> Result({}, String)

The imperative design performs 11 101 effects and is still the fastest writer with evidence passing, because each one is a function call into the page. The patch builds ten thousand operation values in EYG for the page to interpret, and render builds five thousand node records twice and reconciles them. Batching is not free: it moves the work from crossing the boundary, which evidence passing made cheap, to building and reading data on both sides of it.

That changes with generators, where each of the 11 101 effects is a request up the generator chain and the imperative design pays two and a half times as much. The design choice is then about the program rather than the transport. Imperative handles leak, only the removed rows release theirs. Render needs no handles and no lifetimes, and its reconciliation by position is the part a real implementation would replace with keys.

Signals

Task: 200 counters and a derived total, every counter set in each of five rounds.

// host: the page keeps the graph and updates bound text itself
Signal   : String -> Int
Set      : {signal: Int, value: String} -> Result({}, String)
Derive   : {inputs: List(Int), compute: (List(String)) -> <> String} -> Result(Int, String)
BindText : {selector: String, signal: Int} -> Result({}, String)
// handlers: the graph is the state of an EYG handler, writing needs only
WriteText : {selector: String, text: String} -> Result({}, String)

The row <> on compute is the design. The type of the effect requires a pure function, so the page can call it whenever an input changes, from its own event loop, without running a handler or resuming the program. Compiled EYG functions are JavaScript functions, and the row is what makes calling one from outside the program safe.

Host signals do every update in about ten microseconds, and each one calls back into a compiled EYG function to recompute the total over two hundred values. Signals written in EYG are seventy times slower. Every signal operation is an effect handled by a monadic state handler, so it yields and captures a resumption, and the cells are a list because EYG cannot type a tree, so every operation is linear. Their effect count only includes WriteText; the signal operations themselves never reach the page.

Rendering the whole view after every change is ten times slower than host signals. Rendering once per round is the fastest of all, because this task never needs the intermediate states on screen. Signals earn their place when updates arrive one at a time and each must show immediately; when a program can batch, a view as a value is simpler and faster.

WebRTC

Task: connect two peers in the same page and send 2 000 five byte messages over a data channel.

// mirror: the browser API as effects, candidates gathered before a description returns
CreatePeer   : {} -> Int
CreateOffer  : Int -> Result(String, String)
CreateAnswer : {peer: Int, offer: String} -> Result(String, String)
Send         : {channel: Int, data: Binary} -> Result({}, String)
Receive      : Int -> Result(Binary, String)
// batch: the mirror plus
SendAll    : {channel: Int, messages: List(Binary)} -> Result({}, String)
ReceiveAll : {channel: Int, min: Int} -> Result(List(Binary), String)
// session: offers and answers are tokens to carry between peers
Offer   : String -> Result({session: Int, token: String}, String)
Accept  : String -> Result({session: Int, token: String}, String)
Connect : {session: Int, token: String} -> Result({}, String)

All three designs take about the same time, and so do both backends. Connecting two peers and delivering the messages through the page's event loop dominates; every receive is a promise the program waits on, which yields to the host whatever the backend. Batching halves the number of effects and saves nothing measurable. The measurement includes setup, so it cannot say how much batching helps a long-lived channel.

The difference is in what a program has to know. The mirror exposes offers, answers and channels as handles, faithful to the browser API and as leaky as the DOM handles. Session tokens hide SDP and ICE entirely and are strings, so they travel through Copy and Paste, a QR code, or Fetch to a signalling server, with the same speed.

What the language taught

  • Types carry the optimisation. Row types remove most yield checks, and a pure row on an argument lets the host call back into a program. Neither needs anything beyond the types EYG already infers.
  • Tail calls are part of the semantics of handlers. A loop whose effects resume through the handler recurses through the runtime. JavaScriptCore eliminates those tail calls and V8 does not, so on V8 the tail resumptive optimisation decides whether some programs run at all, not how fast.
  • Serialisable values push designs toward data. Handles are forgeable integers that leak without a release effect. Snapshots and renders are ordinary values and need no lifetime.
  • No recursive types means flat trees. It worked twice, for JSON and the DOM, and makes an efficient persistent map impossible to write in EYG, which is why the handler based signals are linear per operation.
  • Purity pays twice. It makes selective translation sound and makes replay a correct implementation of multi-shot resumptions for generators.

Limits and next steps

  • Integers are unchecked JavaScript numbers; the interpreter raises Unrepresentable outside the safe range.
  • !equal on functions compares identity; the interpreter compares closures structurally.
  • References are not compiled, a program must be resolved to one tree first.
  • Calls through variables are checked even when the function is pure, because variables carry opened types. Annotating with the generalised row would remove those checks and their join points.
  • Resumptions that are not tail resumptive grow the stack with each operation. A trampoline in the prompt would make mstate run on V8.
  • The effect designs are experiments. Handles need a release story, render needs keyed children beyond position, and the WebRTC designs do not cover media tracks.
