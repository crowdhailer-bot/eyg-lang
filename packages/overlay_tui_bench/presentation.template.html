03 / Share behavior; isolate the host

The important boundary is below the view.

Host bindings follow Plinth

OpenTUI lives in gleam_opentui, Web APIs in Plinth, and JavaScript, Node and Bun helpers in Plinthx. Keep native objects and receiver-first methods. Fallible calls return Result; thrown values become String(error).

Evaluation cannot block typing

Gleam owns the runtime queue in a separate process. Prompt replies bypass the queued evaluation, avoiding a stdin deadlock. Killing an infinite evaluation leaves the terminal responsive.

04 / Direct @opentui/core bindings

Retain the widget. Change its properties.

A dictionary maps stable run IDs to native rows. New rows are mounted once; existing rows receive changed properties; removed rows are destroyed.

Model update
  → compare screen properties
  → reconcile rows by run ID
  → update changed text / Markdown / visibility
  → OpenTUI schedules layout and drawing

Native widgets already provide scrolling, Markdown, editing, focus, selection and mouse behavior. A second tree is optional.

Hard part: editor coordinates

A cursor can mean a native code-point offset, a Gleam grapheme index, or a terminal display column. Treating those as interchangeable broke Unicode completion.

Coalesce content/cursor notifications in a microtask, derive the grapheme index from the prefix, and preserve the suffix using grapheme slices. Highlight ranges use native offsets.

Tests include Unicode completion, preserved text after the cursor, prompt draft restoration, and real mocked native input.

Trade-off: straightforward lifetime and update logic, but each mutable widget property needs an explicit setter and comparison.

retained view · controller · completion · OpenTUI renderables

05 / A Solid-like graph in pure Gleam

Invalidate first. Pull fresh values. Own cleanup.

Dependency tracking, without JSX

Reads subscribe dynamically; lazy memos cache; writes batch. Dirty propagation completes before effects pull their dependencies, preventing inconsistent diamond reads.

A keyed row owns its signal, subscriptions and native widget. Streaming updates its row; completed rows keep their identity.

Hard part: queued work after disposal

A parent can remove a child whose effect is already queued. Lifetime scopes, rerun cleanup and ordered flushing let the parent dispose it first; queued disposed effects are skipped.

Dedicated tests cover dynamic dependencies, diamonds, nested cleanup, batching, keyed moves and parent/child disposal.

Binding granularity is screen/row, not every JSX expression. No Solid resources, suspense, transitions or error boundaries; unchanged memo results can still wake effects.

06 / Lustre as a terminal renderer

Reuse the real VDOM. Adapt the patch boundary.

view(Model) → Lustre Element(Message)
            → lustre/vdom/diff + cache
            → Mount / Reconcile patches
            → Gleam adapter → retained OpenTUI objects

Declarative tree, stable history

The view defines native widget tags, keys, event handlers and memoized rows. The backend applies insert, remove, replace, move, text and property changes. There is no independently written diff algorithm.

The shared controller owns the reducer and commands. A small Gleam render loop owns the actual Lustre cache.

Hard part: virtual and native trees differ

Fragments and mapped events add virtual boundaries without native layout boxes. A separate metadata tree preserves those paths through keyed moves, keeping mouse handlers attached to the correct messages.

Focus is applied after visibility changes. Child ordering is synchronized only for structural patches.

Pins Lustre 5.7.1 internals. Its JavaScript server runtime has constructor-argument and dispatch-shadowing defects in this version; using the VDOM/cache modules directly avoids a dependency fork.

terminal adapter · render loop · supported properties, runtime findings and upgrade cost

07 / The original TypeScript + Solid implementation

Still a strong baseline.

What it buys

Established JSX, mature ownership semantics, upstream widget types and close alignment with OpenTUI examples. It is the fastest implementation here for typing and populating history.

For a team comfortable maintaining TypeScript, improving this version is a credible alternative to migration.

Hard part: retaining row identity

The baseline replaces an entry object when streaming changes it. Solid's For uses object identity, so that row and its Markdown widget are recreated.

The Gleam versions retain the widget under its run ID. Stable per-row stores or signals could bring the same optimization to TypeScript.

The measured streaming gain is evidence for stable widget identity in these implementations. It does not establish that Gleam is intrinsically faster than Solid or TypeScript.

The comparison keeps the original application behavior unchanged. Its benchmark adapter drives the real App, not a simplified substitute.

08 / Could we bind directly to Zig?

Possible, but the boundary is much lower.

Verified locally

The installed 0.5.14 shared library exports renderer, text/edit buffer, syntax style, native renderable and Yoga-related APIs.

The ABI already includes native renderable support. It is more than a pixel or cell buffer.

Work it transfers to us

Numeric handles, buffer layouts, ownership, native lifetime and platform loading need exact bindings. The public core API still supplies widget behavior, input integration and Markdown orchestration.

Recommendation

Use public @opentui/core objects now. Keep the boundary in gleam_opentui so selected lower-level bindings can be introduced later if profiling justifies them.

This was an ABI and architecture investigation, not a fourth rebuilt frontend or a direct-Zig performance result.

OpenTUI is moving more behavior into native code. Following the public API lets this application benefit without owning that migration.

core package architecture · upstream Zig bridge · upstream native migration direction

Identical events. Native frames. Repeated processes.

5 × 4

Trials × frontends

Fresh Bun processes in rotating frontend order. Two workloads at 20 and 200 completed history rows: 80 trials total.

40 + 120

Warmup + samples

Streaming Markdown chunks or native mocked typing. Each timed update includes decode/input, state, reconciliation and one requested native frame.

110 × 34

Terminal cells

Bun 1.3.14 · OpenTUI 0.5.14 · Linux x64 · AMD EPYC-Genoa. Parser initialized and preloaded before the workload.

Frame latency measures the streaming preview; asynchronous syntax-parser jobs are not all completed within each timed update.

No emulator/display refresh, network, model or evaluator latency. RSS is sampled after parser draining and renderer teardown, without forced GC; it includes native allocations and is not a peak-memory measure. Import timing is inside an already-running Bun process, not cold startup. History timing includes row creation and a frame. Trials ran separately from recording/build work.

12 / The cost after the demo

Choose the abstraction we want to maintain.

DirectionAdvantageOngoing cost
Direct coreSmallest rendering abstraction; explicit identity and lifetimesManual property updates; runtime validation of native options
Gleam signalsReusable reactive computations and owned keyed rowsOur graph scheduler and disposal semantics; incomplete Solid parity
LustreDeclarative view; existing keys, memoization and diff algorithmTerminal patch adapter and coupling to pinned internal modules
Original TypeScriptUpstream types, mature tooling, fastest typing hereSecond application language and runtime boundary; identity optimization remains

Adopt the direct frontend as the next development path. Keep the alternatives as working references, and extract more abstraction when repeated UI complexity makes its value concrete.

All alternatives share the reducer, evaluator protocol, highlighting, completion and host bindings. Changing rendering direction does not require rewriting those layers.
