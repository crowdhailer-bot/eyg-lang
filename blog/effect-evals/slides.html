Overlay answers requests by generating and executing EYG programs. We will start with one real model request, then add only the machinery needed to evaluate a complete agent session. Live observations, implemented mechanisms, and proposed improvements are labelled separately.

01 / Motivation

A plausible answer is a weak release gate.

Prompts change behavior

A new context can help library discovery while making simple tasks slower.

Valid code can be wrong

The first live Fibonacci program parsed, type-checked, and returned the wrong sum.

Success can vary

One working attempt establishes possibility. Repeated trials help measure reliability.

An eval turns “this seems better” into a falsifiable claim about a task, under stated conditions.

Use the result to decide what to change next.

Live Fibonacci evidenceAnthropic: agent evals

Unit tests remain necessary for parsers, handlers, and graders. They do not establish that an LLM will select the right library, recover from an error, or make a good editing decision. A live eval measures that behavior. When a capability becomes reliable, its tasks also protect against regressions.

The practical payoff is a shorter feedback loop: reproduce a failure, define success, change one thing, and inspect whether the result improves. A score is useful only insofar as its task and grader represent work that matters to users.

Fresh means a new Overlay state and workspace for each trial. Prompts within one trial share the session: this supports multi-turn tasks. The transcript stores actual computed EYG values, not only their printed representation. It also records the stopping reason and model-call count.

“Observed effects” is deliberate. The transcript logs the effects exposed at the eval boundary; it is not a complete audit of every lower-level operation. In particular, current time and randomness can be computed inside the browser adapter.

These are independent dimensions, not a ladder where a model judge is automatically more advanced. The Fibonacci eval makes a real model call but uses ordinary value equality. A scripted agent can run through the same full session harness as a real provider.

Capability evaluation and regression evaluation describe the purpose of a suite. Context comparison describes an experiment. Robustness evaluation changes the conditions. None of these requires its own special grading technology.

state.update returns a new State and a list of PAL effects. drain performs one effect, turns the answer into a product message via its continuation, calls update again, and adds the resulting effects to the queue. User prompts advance only after the previous turn has completed.

The model-call limit applies across the whole trial. A bad context stops before the model runs. Storage reads provide model configuration; browser-only features return controlled results. Download and clipboard-write actions are logged rather than performed against the host UI. Host Wait being resumed immediately does not add a Sleep effect to the EYG browser runtime.

web/context.gleamLibrarian context

A context is an EYG value, typically a record of functions and documentation. The loader resolves its dependencies and the product type-checks it. The model can then call context.libraries.search from an ordinary EYG program. It does not need a separate LLM tool for every context function.

That gives two mechanisms worth evaluating separately: the instructions may influence planning, and the API may reduce the amount of code or source knowledge needed. A controlled ablation of text and API would be a useful future experiment; the existing CLI compares complete modules.

environment.answer / Route

The lookup stops at the first answer. Site and hub handling is restricted to the configured origin, including scheme and port. The simple Route record has a different, narrower matching rule. A test of authentication headers, POST bodies, or query behavior would need a more faithful fixture.

Task-declared routes are GET responses. Repository fixtures serve GitHub-shaped URLs without contacting GitHub. Online is available programmatically, but an unmatched request in the normal CLI eval is denied. None of this is an OS network firewall.

module.gleamfixture/

The fixture hub is a local protocol simulation, not a production trust-system test: its release records are unsigned. The module loader can pin named package references to fixture releases, while local imports become content references.

The repository mirror reads local source. Its exclusions for hidden and build directories are conveniences, not a comprehensive secret or symlink policy. Staging a sanitized, fixed source snapshot is preferable when measuring untrusted programs. Do not assume a URL containing /main/ fixes the local repository version used to answer it.

03 / Task design

Write the claim down before running the model.

EYG · excerpt from json_nested_field.eyg

{
  tags: ["libraries"],
  prompts: [
    "An API returned this JSON:
     {\"user\": {\"name\": \"Ada\", \"id\": 7}}.
     Run a program that works out the user's id."
  ],
  checks: [Computes(7), References("json")]
}

Line breaks added; description and reference solution omitted.

Outcome

A program computes integer 7.

Context objective

A submitted program references the existing json package.

Only require a process check when that behavior is part of the task's purpose.

Complete task and reference solutionTask decoder

The task's outcome is deliberately separate from its library-discovery objective. For a generic JSON extraction benchmark, returning the right answer could be sufficient. For a Librarian context eval, reuse of the existing library is an explicit goal.

The checks are independent: Computes accepts any computed matching value, and References scans submitted program syntax. They do not prove the json package was causally responsible for the matching value, or even that the reference occurred in the same successful run. This makes the grader useful but leaves room for stronger checks if that distinction matters.

03 / Deterministic grading

Choose the evidence closest to the claim.

EvidenceImplemented checksExact scope
Returned valuesComputes, SatisfiesAny computed run equals the value or passes an EYG predicate.
Program syntaxReferences, ReadsContextFind a package reference or context field path in submitted syntax.
HTTP interactionFetchesA program fetch got 2xx; URL contains the requested substring.
WorkspaceFileSatisfies, content checks,
WorkspaceUnchanged		Properties of final files or a module evaluated from them.
Agent languageSays, NeverSaysCase-insensitive substring checks on assistant text.

grade.deterministic / passed / score

Property checks can accept multiple valid results without prescribing an exact representation or tool sequence. FileSatisfies loads a module from the resulting workspace and applies the supplied EYG predicate. Syntax-based process checks are weaker: a field access may occur in code that never executes, and a variable named context may be shadowed.

Fetches excludes requests made by the module cache. It demonstrates a successful HTTP response, not that the model understood it. Unknown, including a missing judge, counts as not passing. A trial's stopping reason is recorded but is not independently included in grade.passed: matching checks can pass even if the session later hits a limit. Inspect stopping reasons as well as headline scores.

A passing score is only as strong as the definition of passing. Review checks with plausible counterexamples, including near-miss implementations. The HTTP task is a concrete current gap: it checks method, host, path, and the accept header, but a program could also send a request without failing those assertions.

Do not automatically harden every check into a trajectory specification. Match the observation to the intended user requirement. Final state is often the correct thing to measure; an audit policy about forbidden intermediate actions requires a different observation.

Implementation

One request per judged criterion. Parse a verdict line. Unknown and judge errors do not pass.

Calibration

Human-label examples. Compare recall on human passes, specificity on human failures, and Cohen's κ.

Judge input can be truncated or adversarial. Read the evidence and calibrate before trusting the score.

judge.gleamcalibration.gleam

A judge is another measurement instrument with its own failure modes. Current rendering truncates content, so decisive evidence may be missing. The parser accepts recognized PASS, FAIL, or UNKNOWN lines, using the last recognized verdict. Prompt delimiters do not make hostile instructions in a transcript safe.

The calibrate command generates a labels template without model verdicts. Keep human reviewers blind while labelling: ordinary trial reports include verdicts, so give reviewers transcript-only material. Include both passing and failing examples and report unknown/missing labels separately. A high agreement rate on a mostly passing set can hide a judge that misses almost every failure. Calibration supports review; it does not prove immunity to injection or distribution shift.

These controls run without a model in CI. The oracle is not an alternative measurement of model capability; it proves that the intended solution works against the fixtures and checks. Null failure proves only that doing nothing cannot pass.

A judged-only task cannot receive this deterministic validation. The decoder also rejects empty prompts, empty checks, and nonpositive model budgets. Mutation or counterexample agents are a useful next step because a null agent is a very weak adversary. 03 / Reliability · interactive illustration

“Works eventually” and “works every time” differ.

pass@1
80.0%
pass@k
99.2%
pass^k
51.2%

Illustration only: independent attempts with the same success probability p.

Estimate from n observed trials

If c pass and k ≤ n:

pass@k = 1 − C(n−c,k)/C(n,k)

pass^k = C(c,k)/C(n,k)

C(a,b) is the binomial coefficient. The implementation computes ratios without large factorials.

The current summary uses k = trials per task: “any observed pass” and “all observed passes.”

stats.gleamChen et al.: pass@kτ-bench: pass^k

Move the sliders to demonstrate the difference. The bars show p, 1−(1−p)^k, and p^k under an illustrative independent, identically distributed Bernoulli model. They are not measured Overlay results, and multiplying averages across heterogeneous tasks would be misleading.

The formulas on the right describe the implemented finite-sample estimators. In the current report, k equals the number of trials, so the per-task values collapse to observed any/all indicators. Averaging those indicators across tasks is different from claiming a precise reliability probability for one task. pass@k is useful when a successful attempt can be identified; it does not imply the system knows which of its attempts is correct.

03 / Statistical interpretation

More retries do not create more distinct tasks.

Suite estimate

Compute each task's trial mean. Average those task means with equal weight.

SE = sd(task means) / √N

Reported interval: mean ± 1.96 × SE.

Context comparison

Pair the same task in runs A and B. Estimate the mean task difference.

dᵢ = rate(Aᵢ) − rate(Bᵢ)

Current comparison direction is first run minus second.

The interval is a normal approximation across tasks. Small suites, selected tasks, and repeated tuning limit what it supports.

Inspect per-task regressions and stopping reasons, even when the average improves.

summary.gleamstats.gleamMiller: Adding Error Bars to Evals

Repeated attempts share task difficulty and a common setup. Treating every attempt across the suite as an independent draw of a new task understates the relevant task-level variation. The code therefore computes uncertainty from per-task means and differences. The interval does not include uncertainty from grader mistakes, suite-selection bias, or an unrepresentative deployment distribution.

With one task, the Markdown report says there are insufficient tasks for an uncertainty estimate; the low-level estimator's standard error is zero, not evidence of certainty. The comparison pairs by task name and does not enforce matching fixture or suite identities. Retain that provenance yourself. With only 16 tasks, read normal-approximation intervals cautiously.

03 / Reproducibility

A cassette freezes the model exchange.

RequestMethod + URL + body
→
SHA-256 keyAuth headers excluded
→
Recorded responseStatus + completed stream body

Strict replay

Fail on a changed or missing request. Useful for harness regression and debugging.

Fresh live eval

Needed to measure a changed prompt, context, model, or actual model reliability.

Failed streams are not saved as successful responses. Cassettes do not freeze time, randomness, or all environment state.

cassette.gleamTransport interface

The cassette wraps the transport, so it works with the real provider adapter. It stores the key and response rather than a full raw request. Successful stream chunks are accumulated and saved only when the stream completes. Replay feeds the recorded response back through the product's stream processing.

Strict matching detects request drift. Lenient sequence matching is also implemented, but cannot validate a changed model prompt. A cassette may still contain private information copied into a response, despite excluding authorization headers from the key. To replay a whole experiment faithfully, retain the suite, context, fixture snapshot, and configuration alongside it.

03 / Observability

The score tells you where to look.

summary.md

Task and tag rates, uncertainty, failure groups, model-call and duration summaries.

run.json

Run configuration and structured results for comparisons and judge calibration.

trials/*.md

Prompts, model text, programs, outcomes, observed effects, files, and verdicts.

Read every new failure and sample the passes. A pass for the wrong reason is a grader defect.

The full structured transcript exists in memory. run.json is not a complete event archive for arbitrary regrading.

report.gleamrender.gleam

Failure diagnosis should distinguish invalid generated code, incorrect computed values, bad context loading, fixture mismatch, provider failure, call-limit exhaustion, and grader error. The same red task outcome can have very different causes and fixes.

Rendering and persistence are separate modules. Transcripts may contain model thinking, copied fixture data, and workspace contents. Treat them as potentially sensitive artifacts. The current run JSON is appropriate for aggregate comparisons and calibration but cannot substitute for a complete structured transcript when inventing new graders later.

04 / Sandboxing

Be precise about which boundary is enforced.

LANGUAGE

Generated EYG

Types and managed effects restrict the operations a program can request.

Pure mode grants no external effects.

APPLICATION

Eval harness

Fixtures answer fetches. File effects use an in-memory workspace.

Model traffic takes a separate path.

OPERATING SYSTEM

Host process

The runner can read fixture files and call provider APIs.

No process isolation or resource containment is added here.

Effect control makes experiments easier to inspect.
Resource isolation still needs an outer boundary.

Session boundaryBrowser adapter

The threat model starts with model-generated code and untrusted text in guides, tool responses, or workspace files. The type checker and interpreter restrict the EYG capabilities, assuming their implementation is correct. They do not place the JavaScript host process inside an OS sandbox.

Trusted harness code loads local suites, contexts, and fixtures. The model and judge may receive those data through prompts and transcripts even when program Fetch is offline. This is why “offline eval” must be qualified: it describes the program's fixture environment, not the absence of provider network traffic.

The full runner's timeout applies to a provider request and each read of its stream. It is neither a whole-trial deadline nor fetch cancellation. The pure command does not use that wrapper. Synchronous interpreter recursion can block the JavaScript event loop, so an event-loop timer cannot reliably stop it. Put such execution behind a boundary that another process can terminate.

Now, Random, and Flip are currently resolved inside the browser platform adapter before the eval's effect interpreter can substitute them. Hardening suggestions on this slide are not implemented features. A hardened container runtime such as gVisor can add host isolation; it does not replace an egress policy, safe credential handling, input staging, or explicit resource limits.

These modules keep execution separate from grading and reporting. Graders inspect a completed transcript; they do not restart the agent. File predicates do evaluate the resulting workspace module, so that computation is still real work with its own termination risks. trial timing covers the session execution before grading, not the full time spent on a judge.

Run statistics weight tasks equally. A task's pass flag requires all checks, while its partial score is the fraction of checks passed. These metrics answer different questions and should not be silently interchanged. The current comparison joins on task name; version/provenance checks would be a useful addition.

Appendix D / Actual generated program · attempt 2

The successful Fibonacci program

let sum_fib = !fix((self, count, a, b) -> {
  match !int_compare(count, 0) {
    Eq(_) -> { 0 }
    | (_) -> {
      match !int_compare(count, 1) {
        Eq(_) -> { a }
        | (_) -> {
          let next = !int_add(a, b)
          let rest = self(!int_subtract(count, 1), b, next)
          !int_add(a, rest)
        }
      }
    }
  }
})
sum_fib(20, 1, 1)

Result: 17,710

The current term is added once; recursion advances the pair and decrements the count.

What was checked

For this submitted program, the computed value equals the expected integer.

General correctness, efficiency, and termination on arbitrary inputs were not checked.

Complete live evidence, including the failed first program

This is the actual program from the successful one-shot request, not a hand-written reference presented as model output. Explain !fix as the recursion primitive and !int_compare as producing a tagged comparison value. match consumes tags rather than comparing literal integers.

The input convention matters: starting 1,1 gives 17,710 for twenty terms. Starting 0,1 would be a different task. Clear task wording prevents ambiguity from being mistaken for a model or grading failure.

Appendix E / Review before an untrusted run

Trace both capabilities and data.

Trusted runner process

Host inputs

Suite, predicates, context imports, guides, repository snapshot, provider credentials.

Generated EYG

Type-checked code; managed effects; virtual workspace; fixture HTTP responses.

Provider / judge

Receives prompts, model-visible fixture content, and/or rendered transcripts. Offline program fetches do not prevent this transfer.

Reports / cassettes

May retain source, private file contents, generated text, and copied secrets. Decide access and retention explicitly.

Treat suite files and grader predicates as trusted code in the current design.

Host module loadingJudge inputArtifact output

Four useful review questions: What code is untrusted? Which secrets are available to the host? Which bytes can reach an external model? What can stop an unbounded computation? Model-generated EYG is constrained by the interpreter; a malicious local suite or context import is a separate threat because the host loader has filesystem access.

Stage allowlisted fixtures rather than an arbitrary working checkout, keep credentials out of those fixtures, and run untrusted work with an outer process/resource boundary. Content-addressed modules help identify dependencies, but neither content addressing nor syntactic prompt delimiters establishes that the content is safe.
